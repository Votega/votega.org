# Publishing, sibling repos & open-data conventions

Moved out of `CLAUDE.md` (verbatim, no edits) so the always-loaded file stays short. `CLAUDE.md` points here.

- **The open-data catalog is checked, not trusted** — `_data/open_data.yml` drives `/open-data` (a navbar page) but points at artifacts in the sibling repos, so a publisher that moves a file silently turns catalog entries into 404s. That happened: the `sessions/` migration broke three of seven repo links. `scripts/validate_open_data_links.py` resolves every `files[].url` (GitHub blob → `raw.githubusercontent.com`; site-relative → the working tree) and runs in CI weekly and on change. Weekly matters — the breaking change lands in a *different* repo, so a PR-only trigger cannot catch it. When a publisher's output path CHANGES, update the catalog in the same commit. A NEW artifact is the opposite — publish it first, then add the catalog entry, because the validator runs on push to `main` while most publishers run only on their own schedule. Adding both together advertises a file that does not exist yet and turns the next push red until the publisher happens to fire: `04aaec35` added `data/keywords.json` to `publish_ga_local_government.py` and the catalog together at 12:40 UTC, the validator failed 30 seconds later, and it stayed red until `update-local-government.yml` published the file at 12:51. Eleven minutes there, but that workflow is twice-weekly, so the window is normally days. The `ga-district-information` entry shows the right order ("Files now exist in the sibling repo; the link validator resolves all 36 catalog links"). If both must land together, dispatch the publisher manually straight after merging.

- **Reuse terms are emitted, never hand-copied** — VoteGA data is published under **CC BY-SA 4.0** (site code is PolyForm Noncommercial 1.0.0; see `LICENSE`/`NOTICE.md`). `scripts/lib/sibling_publish.py` injects `LICENSE` (canonical SPDX legalcode, so GitHub detects it) and `NOTICE.md` (the attribution string) into every publish automatically; no publisher needs to opt in and none can omit them. The upstream name comes from `REPO_SOURCES`, keyed by **target repo, not publisher** — two publishers write to `ga-legislation`, and per-publisher sources would rewrite `NOTICE.md` against each other on every run. Adding a new sibling repo means adding it to `REPO_SOURCES`; publishing to an unregistered repo raises rather than emitting an uncredited notice. Do not add a per-dataset license field to `open_data.yml` — the license is stated once on the page and once in the publisher.

- **Published files name their own session** — `Votega/ga-legislators` (`scripts/publish_ga_legislators.py`) overwrites `data/all.json`, `data/members.csv` and `ROSTER.md` IN PLACE at a biennium rollover; only the deliberate `freeze-roster` run preserves the outgoing roster under `sessions/<slug>/`. So a downloaded copy must say which General Assembly it describes: `members.csv` carries a constant `session` column (15th; find it by header name, since `votegaUrl` is appended after it) (from `ga-members.json` `metadata.session`; the publisher exits 1 if it is missing), `members.schema.json` describes `metadata.session` / `legisSessionId` / `generatedAt` and points at `sessions/` for history, and the live `ROSTER.md` heading names the session. The same rule is applied to the session-partitioned files: `votes.csv` ends with `session` and `scorecard.csv` (biennium grain) with `biennium`. New CSV columns are APPENDED, never inserted, so positional consumers keep working; schemas gain `properties` but no new `required`. Pinned by `scripts/test_publish_ga_legislators_session.py`. A new publisher whose output is overwritten per cycle should carry its scope the same way.

- **A Congress turnover is a recognised path, never a bypass** — `scripts/lib/federal_turnover.py` compares the committed roster's `metadata.congress` (falling back to the sponsorship index's) with `lib/congress_session`. Inside a Congress, >25 members flagged departed still fails the roster run, and `validate_current_members.py` refuses the same drop. At a turnover the run requires a FINAL `sessions/<slug>/freeze.json` in `Votega/ga-federal-legislators` (the votes run requires it too), allows the departures, and requires sanity instead (500-541 members, Georgia 2+14 filled or declared vacant, >=90% with a term in the new Congress); it writes `metadata.rollover`, which the validator demands for any changed Congress. If Congress.gov does not yet list the new Congress the run HOLDS (exit 0, writes nothing) for 7 days, then fails. Tests: `test_federal_turnover.py`; runbook RECURRING-TASKS.md §3b.
- **A finished Congress is frozen before the 120th overwrites it** — `Votega/ga-federal-legislators` `data/` is replaced in place when a new Congress is seated, and `lib/congress_session.py` derives the Congress number from the UTC date, so it flips at 00:00 UTC on 3 January (11 hours before the new Congress convenes at noon Eastern). `python scripts/publish_federal_delegation.py freeze [119th] [--final] [--overwrite]` (workflow `freeze-federal-delegation.yml`, manual) writes the Georgia delegation's roster, votes, party-unity scorecard and full sponsorship record to `sessions/<ordinal>/`, with per-path schema `$id`s, a `freeze.json` manifest and a README. Run it provisionally any time and **`--final` by 2 January 2027**, after the last roster, votes and sponsorship workflows have committed. Guards: it refuses to file data from a different Congress under the slug (after 3 January the live files are the 120th's, so a late run would otherwise mislabel them), refuses to replace a final freeze without `--overwrite`, and the daily publish refuses to write anything under `sessions/`. Every live CSV ends with a `congress` column. Tested by `scripts/test_publish_federal_delegation_freeze.py`. Adding a source file to the frozen record means adding it to `build_freeze`, with a check that it describes the same Congress.

- **Every publish is gated before the PUT** — `publish_or_dry_run` in `scripts/lib/sibling_publish.py` runs `_assert_artifacts_sane` on the way out (before both the live publish AND the dry-run, so local/CI runs fail identically): it refuses to push an empty artifact set, any empty-byte artifact, or any `*.json` that does not parse. This is the choke point every publisher calls, so the guard cannot be forgotten by a new one; it exists because publishers `json.load` local disk and PUT with a standing write-PAT and nothing else re-checks the bytes (PIPELINE-AUDIT.md #1), and it reinforces the atomic-write fix (#2). For a dataset record floor, pass `validate=min_items("<primary artifact>", "<collection>")` — a corpus-independent non-empty check that catches a well-formed-but-empty dataset (valid JSON, so the sanity guard passes) before it wipes a public repo. Use it only for FLAT, always-populated datasets (races, ballot-measures, federal delegation, the members roster, the local-gov registry); do NOT add it to the session-partitioned publishers (`publish_ga_bills`, `publish_ga_legislators` votes/scorecard/freeze-roster), which emit empty sessions by design and would false-positive — the universal sanity guard still covers them.

- **A published schema declares the path it lives at, and carries a version** — `$id` is a JSON Schema document's canonical identity, so two files must never share one. Build it from the artifact's own published path (`schema_url(schema_path)` in `publish_ga_legislators.py`), never a hardcoded literal: with literals, every session's `sessions/<slug>/votes.schema.json` claimed to be `sessions/votes.schema.json` — a URL no file occupies — and the frozen roster's copy claimed to be the live `data/members.schema.json`, so a resolver caching by `$id` could serve one session's schema for another's data. Each schema also carries `schemaVersion` (the `SCHEMA_VERSION` constant) and a `schemaStability` string, reusing the vocabulary `id-crosswalk.json` already publishes in its metadata. `schemaStability` is where a guarantee the schema cannot express goes: `metadata.session` is deliberately **not** `required`, because snapshots taken before the 2026-10 legis.ga.gov migration predate the field and would stop validating — but the publisher `sys.exit`s rather than emit a roster without it, so `required` would add nothing a consumer cannot already rely on. Adding `required` to a published schema is a breaking change for anyone validating an older copy; prefer describing the guarantee. `scripts/test_publish_ga_legislators_session.py` pins the `$id`-matches-path, no-collision and version invariants.
- **Link the published dataset, not the internal asset** — whenever a page renders data we also spin off into a sibling repo (a `publish_*.py` → `Votega/<repo>`), that page's data/source footnote MUST link to the published repo, not the raw `assets/data/*.json` path it happens to fetch. The internal asset is a build artifact (often destructively replaced at a session/cycle rollover); the sibling repo is the stable, archived, multi-format (JSON/CSV/schema) open-data home. Prefer the repo's stablest location for the data on screen (e.g. the matching `sessions/<biennium>/` dir), built from metadata so it self-updates, with a fallback to the repo root. Match how `about-the-data.md` already cites that repo. Precedents: `ga-party-unity.html` → `Votega/ga-legislators`, `ga-executive-orders.html` → `Votega/ga-executive-orders`. Known sibling datasets whose source pages should follow this: ga-federal-legislators, ga-legislators, ga-legislation (bills + ballot measures), ga-executive-orders, ga-races-elections.
- **Renaming a workflow means updating the failure-notifier in the same commit** — `notify-workflow-failure.yml` watches other workflows via `workflow_run`, which matches on the workflow's exact `name:` string. Change a workflow's `name:` (even trivially, e.g. `(daily, 08:15 UTC)` → `(twice daily)`) and its notifier entry silently watches nothing — the workflow then runs unattended, so a failure opens no issue and looks identical to a clean run. `scripts/validate_workflow_triggers.py` catches this (it fails CI when a scheduled workflow is unwatched or a notifier name matches no workflow), but it's a two-file change: edit the workflow's `name:` **and** the matching line in `notify-workflow-failure.yml`'s `workflows:` list together. Run the validator locally before pushing.
