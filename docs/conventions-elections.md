# Elections, races & candidate conventions

Moved out of `CLAUDE.md` (verbatim, no edits) so the always-loaded file stays short. `CLAUDE.md` points here.

- **The in-place `races.json` writers guard before they overwrite** — `races.json` is the core of the elections section and ~7 scripts read-and-overwrite it in place. Each takes a `copy.deepcopy` snapshot right after `json.load` and, immediately before `write_json_atomic`, runs the matching check(s) from `scripts/lib/races_guard.py`, aborting with `RacesGuardError` (no write — atomic, so disk is untouched) on a violation. The invariants are writer-specific: `assert_phase_transitions` (only `primary→general` / `runoff→general`, right count, non-empty resulting ballot) for `update_general_from_primary`/`_runoff`; `assert_active_phases_unchanged` for `fix_general_fallbacks`; `assert_active_phases_unchanged` + `assert_membership_preserved` (candidate id-set/count/`type` unchanged per phase) for `sync_candidate_profiles`; `assert_only_race_changed` for `set_general_candidates`; `assert_equal_except(..., "updatedAt")` for `stamp_races_updated_at`; `apply_overrides` keeps its own positional-id guard. All build on `assert_race_set_preserved` (no race added/dropped, no top-level key lost) — the check that catches the headline #3 risk of a bug silently shrinking the roster. The snapshot is the baseline, NOT git HEAD (these run manually against uncommitted trees). When adding a new `races.json` mutator, wire the appropriate guard the same way. (PIPELINE-AUDIT.md #3.) **The push path is guarded too:** `scripts/validate_races.py` (tests: `test_validate_races.py`) runs as a step in the publish and both refresh workflows that fire on a `races.json` push, covering hand edits that bypass the script guards (e.g. `tools/race-candidate-editor.html`). Absolute checks always run (unique ids, a populated activePhase, a recorded winner on that race's ballot); change checks run against the pre-push commit (race set, forward-only phase moves, a >5% candidate drop, a replaced/removed winner). A deliberate structural change needs `[races-structure-change]` in a pushed commit message, which relaxes the change checks only.

- **Entity share cards are generated at deploy, never committed, and fall back to the default.** `build_entity_pages.py` queues one row per entity (`add_card`) into `.share-cards/manifest.json`; `scripts/build_share_cards.py` (a deploy-pages.yml step between "Generate entity pages" and Jekyll) draws each row with headless Chrome into `assets/img/share/<section>/<slug>.png` and only then adds `share-img:` to that page's front matter, so an entity whose card did not render keeps `og-default.png`. Both paths are gitignored (~100 MB of PNGs would bloat history). Layout lives in `scripts/lib/share_card.py` (pure, tested by `scripts/test_share_cards.py`) and follows the style guide's entity card: party colour only on the party pill, the same layout for every candidate in a race, nothing under 24 px, headline 48 px or more. **A candidate gets a card only while on the race's ACTIVE ballot** (`candidate_card_lines`, from `_race_active_candidates`: the general once it exists, else runoff, else primary), so someone who lost out keeps `og-default.png` and no card implies they are still running; this is derived from the data, never a per-cycle list. The distinguishing line is per office: occupation and county for GA House/Senate (the only filings that carry them), the opponents ("vs. A (D), B (R)") for everyone else, so cards differ across offices but never within a race. **Portraits come only from `candidate-image-cache.json` (government hosts), so a candidate (no cached photos exist for them) gets the monogram circle, never a campaign photo.** The renderer refuses to draw if Public Sans did not load, rather than ship fallback-font cards. A new entity type means a new `add_card` call in its builder, not a new template system.
- **A candidate off the race's current ballot is "retired": kept, labelled, and unadvertised, never deleted.** `candidate_standing()` in `build_entity_pages.py` (built on `lib/candidate_standing.py`, the same active-ballot rule as the share cards, derived from `races.json`; off-ballot or lost counts as retired) marks anyone not on the race's active ballot once that ballot exists. Their page keeps working (old links, shares) with a "No longer on the ballot" banner, `noindex`, `sitemap: false`, and no directory entry; their id is listed under `retired.candidate` in `entity-urls.json`, which the two search surfaces read through `VoteGA.entityUrls.isRetired` to hide them. **Never drop a retired candidate from `search-entities.json` itself**: the page builders read that index back to know which pages to generate, so removing a record deletes its page (the same trap `entity-urls.js` describes for rewriting its URLs). Set `entity.retired` only when true, or every live candidate's content hash, and so its sitemap `lastmod`, changes. **Decided races use the same machinery** (`scripts/lib/candidate_standing.py`, tested by `test_candidate_standing.py`): when a race is `status: "certified"` with `winner.candidateId` in `races.json`, the winner's candidate page redirects (`redirect_to`, via jekyll-redirect-from) to their officeholder page and every other candidate in it is retired with "Election decided" wording. The redirect target comes from `id-crosswalk.json` (the candidate id and the bioguide/roster id sit on the same person), never from a name, and only when that page exists: a winner who is not on the roster yet keeps their page with a "Won this election" note and redirects on the first deploy after the roster carries them. Nothing changes on unofficial results, and a recorded winner id that matches nobody in the race is ignored rather than marking everyone "lost". A person in several races (a special and a full term) is live if live anywhere, else won if they won anywhere. **The trigger is `status`/`winner` on the race, recorded by `scripts/propose_race_winners.py` after a person reviews it.** It reads the certified results (`_data/election_results/*.json`, gated on the results page's `status: certified`), ties each result to a race by **election date** (races.json calls both the June primary runoff and a December general runoff "runoff"), requires a **majority** (a plurality is a runoff; within half a point of 50% is flagged), and matches the winner by name within that race's ballot only if exactly one candidate fits (`lib/race_winners.py`, tested by `test_race_winners.py`). The default run only prints a report (would-record, runoffs, and everything it declined with the reason); `--apply` writes only the unambiguous ones behind `races_guard.assert_only_winners_changed` and refuses to touch a different winner already recorded. **An incumbent running for re-election is listed by `memberId` only** (no name, no candidate id), so a win by one is recorded as `winner.memberId` (names come from `current-members.json`) and `candidate_standing` treats every candidate-id candidate in that race as lost. Judicial races are counted but not matched yet. Run it after the Secretary of State certifies and the results page says so, review the diff, commit.
- **Never put a status word in a post's filename, slug or permalink.** A post's URL comes from its filename (`_posts/YYYY-MM-DD-<slug>.md`), so a slug like `...-unofficial-results` is wrong the day the results certify, and renaming it breaks every inbound link, share and `home_results_post.url`. Name posts for the topic (`georgia-general-assembly-majority-2026`), and keep "unofficial"/"certified" in the title, body and the `home_results_post.label` in `_config.yml`, which can change freely. The existing `2026-11-04-georgia-general-assembly-majority-unofficial-results` post is the cautionary case: its URL stays as is (or gets a `redirect_from` if it is ever moved), and its title/notice must be updated by hand at certification. The `home_results_post` label should likewise avoid status words so it needs no edit at the flip.
- **Election night: publishing a count (the runbook).** Run the **Publish election results** workflow (`.github/workflows/publish-results.yml`) from the Actions tab or the GitHub mobile app: paste the Secretary of State's export URL, pick the `data_key`, press Run. The URL to use is the **JSON feed**, which is stable all night:
  `https://results.sos.ga.gov/cdn/results/Georgia/export-<MMDDYYYY><ElectionName>.json` (2026 general: `export-11032026GeneralAndSpecialElection.json`). The XLSX workbook the results site offers carries a fresh GUID in its download name every time, so it can only be fetched by hand; the builder reads either, plus a CSV of the workbook's first sheet. The export is the SoS's **XLSX workbook** (three sheets; `Total Votes` is the one parsed) — `build_results_json.py` reads it directly, stdlib only, and also takes a CSV of that sheet; if there is no stable URL, commit the file and pass `csv_path` instead. It fetches the export, rebuilds `_data/election_results/<key>.json`, refuses it if it looks wrong (`scripts/validate_results_build.py`: no votes at all, a ballot that shrank, counts going backwards, structural damage), commits, and dispatches the deploy — then verifies a deploy run actually started, because `deploy-pages.yml` fires on human pushes plus crons at 13:00 and 23:00 UTC (6pm ET, before polls close), and a GITHUB_TOKEN commit raises no `push` event. Leave `fill_missing` ON for unofficial counts so a partial export cannot delete the rest of the ballot from the page (races it does not mention keep reading "Awaiting Results"); turn it OFF for the certified rebuild, which should be exactly what was certified. Nothing on the results page needs flipping on election night — the first counted vote switches the badge and notice on its own; `status: certified` and `updated:` are the only hand edits, at certification. The same sequence by hand is `python scripts/build_results_json.py <csv> <data_key>`, commit, push to main as a person.

- **After an election: recording winners (the runbook).** The candidate-page behavior above only fires once `races.json` carries `status: "certified"` and a `winner` on each decided race, and `scripts/propose_race_winners.py` is how those get there. In order: (1) **Election night**, once the results JSON holds counts: `python scripts/propose_race_winners.py --preview-unofficial` (report only; it can never be combined with `--apply`) to check that the real file's names and structure match, and fix anything under "Needs a person" by correcting the ballot name in `races.json` or the results file. (2) **A race with no majority** is listed under "No majority, so a runoff" and gets no winner; set it to `activePhase: runoff` as usual and re-run after the runoff results certify (a later certified set supersedes it). (3) **At certification**, set the results page's `status: certified` (and `updated:`), then run `python scripts/propose_race_winners.py` and read the report: every "Needs a person" line is a race it declined to decide, and a CONFLICT means a different winner is already recorded (the tool never overwrites one). (4) `python scripts/propose_race_winners.py --apply`, review `git diff assets/data/races.json` (only `status`, `winner` and `updatedAt` change), commit and push. Candidate pages then redirect or retire on the next deploy; a winner whose officeholder page does not exist yet keeps a "Won this election" page until the roster carries them (federal roster updates after the January swearing-in, the GA roster at the 2027-01-11 biennium rollover). Judicial races are not matched yet.

## Results pages and publishing

One results page per election, `/<slug>-results/` (`layout: election_results`), backed by `_data/election_results/<results_data>.json`. Listed in `_data/election_archive.yml`, which drives `/results/` and the home page Election Results card. The page front matter is the source of truth for status; the archive's `status` is only a fallback.

**Front matter that matters.**
- `status`: `unofficial` until the Secretary of State certifies, then `certified`. With `updated:`, it is the only hand edit at certification.
- `results_folder`: the permanent folder under `results/` in Votega/ga-races-elections. Set it when the page is created, and never change it once published.
- `notice_upcoming`: shown until the first counted vote, then it drops away on its own. Never name it `notice`, which stays above the results.
- `results_mode` (`round` / `final`), `runoff_advances`, `label_*`, `race_notes`, `district_lookup`, and `county_map` (the map shows only once `certified`).

**Before election night (stage the page).**
- Create the page and its data file with every contest and candidate at zero votes, built from the SoS's staged export, so it reads "Upcoming" / "Awaiting Results". Add the election to `election_archive.yml`. Point `publish-results.yml`'s `data_key` default at it.
- Make it indexable as soon as it exists: no `noindex`, no `sitemap: false`, no `search: false`. The point is for the URL to be indexed before people search on election night.
- **A staged page must not read as empty**, or Google files it as a soft 404 (#528).
  - Pages with 25 or fewer races carry the races and candidates in the served HTML, not only after scripts run.
  - Empty sections write nothing.
  - Before polls close, each contest says when votes will be reported.
- Write `share-description` for the election, not for its status ("results for …, with counts after polls close at 7 PM ET").
- After the deploy, run **Test live URL** in Search Console and request indexing. This step is manual.

**Election night and certification.**
- Election night: run **Publish election results** with the SoS JSON feed, `fill_missing` on and `commit_csv` off; see the pipeline section above. Nothing on the page needs flipping; the first counted vote switches the badge and notice.
- Certification: rebuild with `fill_missing` off from the certified export, and commit the export to `_sources/election_results/`. Set `status: certified` and `updated:`, then record winners (runbook above).
- A contest the SoS published no certified count for stays on the page with a "No Certified Count" note, never zero votes. Example: Waycross DA, 2026 general.

**Open data (Votega/ga-races-elections).**
- Only `status: certified` pages publish (`publish_results.py`, `publish-results-to-ga-races-elections.yml`, on push, after Publish election results, and daily). Unofficial counts are never published there.
- Each certified page gets `results/<results_folder>/`:
  - `results.json`, `results.csv` and `results.schema.json`;
  - `county-results.csv` where the SoS JSON export exists (distilled to `_sources/election_results/<key>-breakdown.json`);
  - plus `data/results/manifest.json`.
- A missing count or vote-method split is blank (`not-reported`), never 0.
- Certified pages carry a source footnote linking their published folder.
- Add the `/open-data` catalog entry only after the first publish.

**Home page.**
- The Election Results card lists the two newest entries from `election_archive.yml` with the same badges as `/results/`. It is built at deploy, so badges change on the next deploy.
- Turn the Next Election card on (`home_next_election: true`) once the previous election is certified.
- A small election (one district) sets `hideSampleBallot: true` in `ga-election-calendar.json`.

**URLs.** No status words in any results URL or post slug (see above). The page URL and `results_folder` are permanent, so the badge, title wording and notices carry the status.

**IndexNow** runs on its own after every deploy (`indexnow.yml`). Search Console indexing requests stay manual.
